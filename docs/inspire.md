# Monitra 软件灵感

## 一、Monitra 是什么

Monitra 是一套面向交通基础设施运营期健康监测、长期性能观测、风险研判和科研应用的软件系统。

它服务的对象可以包括：

* 桥梁；
* 隧道；
* 边坡；
* 路基；
* 路面；
* 涵洞；
* 冻土路基；
* 未来可能扩展的其他基础设施。

Monitra 希望解决的不是某一种设施、某一个设备或某一个项目的数据展示问题，而是建立一套可以长期承载不同运营期监测项目、不同设施、不同监测方式和不同参与单位的通用数字化平台。

在这个平台中，现实中的工程设施、监测位置、监测指标、设备、数据、风险、专业研判、通知与反馈过程和交付成果可以被连接起来。

系统最终需要回答一系列连续的问题：

```text
正在管理哪些项目和设施？
这些设施的结构和监测对象是什么？
在哪里进行监测？
具体监测什么内容？
哪些设备或数据来源正在提供数据？
数据是否正常、完整和可信？
设施当前是否存在风险？
风险依据是什么？
风险需要由谁研判并通知相关人员？
研判、通知和反馈进行到了哪一步？
最终形成了哪些报告、数据和成果？
所有结论是否可以追溯到原始证据？
```

Monitra 可以理解为交通基础设施监测领域的数字化业务底座。

它既需要支持运营期监测项目的实施、交付和长期运行，也需要支持风险研判、数据积累、科研分析和成果生产。

---

## 二、Monitra 不应只是一个什么系统

Monitra 不应只被理解为：

* 一个设备管理后台；
* 一个传感器接入平台；
* 一个实时数据看板；
* 一个告警列表系统；
* 一个报告生成工具；
* 一个单项目定制化系统；
* 一个科研数据仓库；
* 一个领导大屏系统。

这些能力可能都会出现在 Monitra 中，但它们只是完整系统的一部分。

Monitra 更核心的价值，是在这些能力之间建立连续关系：

```text
现实设施
→ 监测对象
→ 数据来源
→ 监测数据
→ 数据可信度
→ 风险判断
→ 专业研判、通知与反馈
→ 报告与成果
→ 长期数据资产
```

如果这些环节彼此割裂，即使每个模块都存在，系统仍然只是多个工具的集合。

Monitra 希望形成的是一套完整的监测业务体系。

## 三、Monitra 所面对的真实业务世界

Monitra 的业务世界中可能同时存在以下内容：

### 1. 多个项目

平台可能同时管理不同地区、不同业主和不同类型的项目。

项目用于运营期安全监测或长期性能观测。项目持续产生的监测数据，可以在独立授权后被一个或多个科研分析使用，但科研本身不从属于某个项目。

不同项目之间可能共享：

* 设施类型；
* 指标定义；
* 设备产品；
* 协议解析规则；
* 监测模板；
* 告警规则模板；
* 报告模板；
* 数据标准；
* 可视化能力。

系统不能要求每新增一个项目就重新开发一套软件。

### 2. 多种基础设施

不同设施的结构、监测方式和关注风险存在明显差异。

例如：

* 桥梁可能关注主梁位移、应变、索力、支座状态和结构振动；
* 边坡可能关注深部位移、地表位移、地下水位和降雨；
* 路基可能关注沉降、孔压和含水率；
* 冻土路基可能关注地温、冻融深度、含水率和沉降；
* 隧道可能关注收敛变形、沉降、裂缝和环境状态。

Monitra 需要允许这些设施保持专业差异，同时又建立统一的数据和业务基础。

### 3. 多种参与单位

一个项目中可能同时存在：

* 业主单位；
* 运营养护单位；
* 项目公司；
* 监测单位；
* 设计单位；
* 专业检测单位；
* 项目管理或咨询单位；
* 设备厂家；
* 系统集成商；
* 监管单位；
* 平台运营或技术支持单位。

这些单位可能只参与业务，不一定都需要成为系统中的独立客户或独立运营空间。

因此，Monitra 需要能够区分：

* 现实中的组织和业务单位；
* 软件中的管理与数据隔离范围；
* 项目参与关系；
* 用户实际获得的访问权限。

具体采用什么身份结构、入口形式和交互方式，需要在后续产品设计中继续推导，而不是仅由现实组织关系直接决定。

这里需要区分五类不同概念：

* Organization 表示现实中的业主、监测单位、科研单位等组织；
* TenantSpace 表示软件中的数据隔离和管理范围；
* Project 表示一次运营期监测业务及其交付范围；
* Facility 表示被监测的桥梁、隧道、边坡、路基等现实设施，并具有可以跨项目识别的稳定身份；
* Deployment 表示一套独立安装和运行的 Monitra 软件实例。

现实组织不必与租户空间一一对应，项目也不等同于租户或软件部署实例。

### 4. 多种数据来源

监测数据可能来自：

* 传感器；
* 数据采集仪；
* 边缘网关；
* 厂家平台；
* 第三方监测平台；
* 文件导入；
* 人工录入；
* 外部算法或计算系统；
* 历史数据迁移。

这些数据的传输方式、格式、质量和可靠性可能完全不同，但进入 Monitra 后，需要逐步形成统一、可查询、可追溯的业务数据。

## 四、Monitra 的核心业务对象灵感

以下对象可以作为理解系统的起点，但不代表最终的数据模型和模块边界已经确定。

## 1. 项目

项目是围绕一项运营期健康监测或长期性能观测任务，组织一个或多个基础设施、监测方案、设备、数据、风险研判和交付成果的业务容器。

项目中可能包含：

* 项目基本信息；
* 真实参与单位；
* 项目人员；
* 设施和资产；
* 监测方案；
* 设备和接入配置；
* 数据；
* 风险、专业研判和反馈记录；
* 报告；
* 成果；
* 权限和数据范围；
* 项目运行状态。

项目不应只是一条基础信息记录，而应承载完整的监测业务上下文，也是常见的系统交付、用户协作和数据组织边界。

例如，一个桥梁健康监测项目可以同时包含三座大桥。三座大桥分别作为项目中的设施存在，共享这个项目的参与人员、交付要求和运行范围，同时保留各自独立的设施结构、监测方案、设备、数据、告警和成果。

同一座现实设施在合同续约或新的运营监测任务中，可以被新的项目继续关联，而不需要复制成另一座设施。项目仍然是每次监测业务和交付的独立边界；监测方案、项目人员、设备配置、权限、数据、告警、报告和成果仍按项目分别管理。

跨项目识别为同一座设施，不代表不同项目自动共享数据或权限。只有在部署范围、用户权限和数据授权都允许时，系统才可以围绕同一设施建立跨项目的历史关联或连续分析。

## 2. 资产与设施结构

Monitra 需要描述现实基础设施的组成关系。

系统需要区分设施的稳定现实身份与它在某个项目中的具体监测上下文。Facility 用于回答“现实中是不是同一座桥、同一条隧道或同一处边坡”，Project 则用于回答“本次监测任务以什么方案、人员、设备、权限和成果对它开展工作”。

例如一座桥梁可能包含：

```text
桥梁
├── 上部结构
│   ├── 主梁
│   ├── 桥面
│   └── 监测断面
├── 下部结构
│   ├── 桥墩
│   ├── 桥台
│   └── 基础
├── 支座系统
├── 伸缩缝系统
└── 环境监测区域
```

一处冻土路基可能包含：

```text
冻土路基段
├── 观测断面
│   ├── 地温孔
│   ├── 水分孔
│   ├── 沉降点
│   └── 气象观测位置
├── 工程措施
│   ├── 热棒
│   ├── 通风管
│   └── 块石结构
└── 周边环境区域
```

这种结构不仅用于管理设施，还可能成为：

* 监测对象的组织基础；
* 空间展示基础；
* 数据查询范围；
* 权限范围；
* 报告组织结构；
* 成果归档结构；
* 风险定位依据。

不同设施是否统一采用树形结构、如何处理断面、测孔、构件和空间区域，还需要在后续设计中进一步验证。

## 3. 监测位置

系统需要表达“在哪里进行监测”。

例如：

* 桥梁主梁上的一个 GNSS 点；
* 边坡上的一个深部位移测孔；
* 隧道中的一个监测断面；
* 路基上的一个沉降点；
* 冻土路基中的一个地温孔。

监测位置与工程资产有关，但不一定与资产采用完全相同的建模方式。

某些对象需要独立的台账、GIS、附件、权限和生命周期，可能更接近资产。

某些对象只是具体的测量位置，可能更接近监测点。

这部分边界需要在后续设计中结合真实项目案例继续推导。

## 4. 监测指标

系统需要表达“具体监测什么”。

可能包括：

* 位移；
* 沉降；
* 应变；
* 裂缝宽度；
* 索力；
* 加速度；
* 倾角；
* 地下水位；
* 孔隙水压力；
* 雨量；
* 气温；
* 地温；
* 含水率；
* 冻融深度；
* 电量；
* 信号强度。

指标可能具有：

* 名称；
* 单位；
* 数据类型；
* 精度；
* 适用设施；
* 适用测点；
* 统计方式；
* 质量要求；
* 告警含义；
* 外部标准编码。

平台可以沉淀公共指标，也需要允许项目根据实际情况扩展特殊指标。

## 5. 业务监测通道

同一个监测位置和同一个指标，还可能存在不同方向、深度、分量、层位或位置。

例如：

```text
GNSS01 + 位移 + 东向
GNSS01 + 位移 + 北向
GNSS01 + 位移 + 垂向

地温孔 T01 + 地温 + 深度 0.5m
地温孔 T01 + 地温 + 深度 1.0m
地温孔 T01 + 地温 + 深度 2.0m

测孔 ZK01 + 深部位移 + 深度 10m + X方向
测孔 ZK01 + 深部位移 + 深度 20m + X方向
```

系统需要有一个稳定对象，代表最终被持续观测、查询、统计、告警、报告和导出的业务数据通道。

需求文档将这个对象称为 MonitorChannel。

MonitorChannel 是当前非常有价值的核心概念，因为它能够把以下内容连接起来：

* 监测位置；
* 指标；
* 方向和深度等维度；
* 设备数据；
* 时序数据；
* 最新值；
* 数据质量；
* 风险判断；
* 报告；
* 大屏；
* 科研分析。

但是 MonitorChannel 的最终属性、状态模型、生命周期和与其他对象的边界，仍然可以在后续设计中继续审查。

## 6. 设备、设备字段与业务数据

现实中的采集设备和业务监测对象并不是同一个概念。

系统需要管理：

```text
设备厂家
→ 设备产品或型号
→ 设备实例
→ 设备上报字段或原始通道
```

例如某个设备上传字段：

```text
CH01
temperature_01
displacement_x
sensor_value_3
```

这些只是设备侧的数据表达。

系统还需要把设备字段映射到具体的业务监测通道。

这种解耦可以支持：

* 同一设备产品复用解析配置；
* 个别设备覆盖默认配置；
* 设备更换后业务历史保持连续；
* 一个设备为多个监测对象提供数据；
* 一个业务通道在不同时间使用不同设备；
* 厂家字段变化时不影响上层业务定义。

具体如何设计设备产品、设备实例、原始通道和绑定关系，需要在后续设备接入专题中细化。

## 7. 原始数据与业务数据

系统可能需要同时保存不同层次的数据：

* 接收到的原始报文；
* 协议解析后的结构化结果；
* 设备字段；
* 设备与业务通道的映射结果；
* 转换后的业务值；
* 数据质量评价；
* 最终时序数据；
* 最新值；
* 后续计算结果；
* 风险和告警。

这样可以在出现问题时回答：

```text
这条数据最初是什么？
由哪个来源提供？
什么时候接收到？
使用了什么解析规则？
识别成了哪个设备？
绑定到了哪个业务通道？
是否进行了换算？
为什么被判定为有效或异常？
是否参与了风险计算？
最终被哪些报告或成果使用？
```

这条可追溯链路是 Monitra 区别于普通数据展示系统的重要能力。

## 五、Monitra 可能包含的主要产品能力

以下内容描述的是 Monitra 可能覆盖的业务能力范围，不表示最终一定按照这些模块、菜单或工作台进行划分。

## 1. 平台基础管理

为了支持多个项目和长期复用，系统可能需要维护：

* 业务单位和组织；
* 客户或租户范围；
* 用户；
* 项目参与关系；
* 权限；
* 数据访问范围；
* 平台字典；
* 指标库；
* 资产类型；
* 设备厂家和产品；
* 协议解析能力；
* 项目模板；
* 报告模板；
* 外部编码映射；
* 系统审计。

这些能力的核心目的不是建设一个庞大的后台，而是让新项目中的共性内容可以沉淀并复用。

## 2. 项目实施与初始化

Monitra 需要支持一个项目从空白状态逐步形成完整监测体系。

这个过程可能包括：

```text
建立项目
→ 明确参与单位和人员
→ 建立设施结构
→ 建立监测位置
→ 配置监测指标和业务通道
→ 配置设备
→ 建立设备与业务通道关系
→ 配置数据接入
→ 验证数据
→ 配置风险规则
→ 配置报告和展示
→ 进入正式运行
```

对于大型项目，系统还可能需要：

* 项目初始化模板；
* 资产模板；
* 测点和指标模板；
* 批量导入；
* 批量校验；
* 错误清单；
* 配置复制；
* 项目级调整；
* 配置版本记录。

具体的项目实施和初始化流程不应在灵感阶段写死，需要结合实际实施人员的工作方式进行设计。

## 3. 设备与数据接入

Monitra 需要接收不同设备和外部系统的数据。

可能支持：

* HTTP JSON；
* MQTT；
* Excel或CSV；
* 人工录入；
* 第三方平台推送；
* 第三方接口拉取；
* 后续扩展的其他接入方式。

设备接入能力可能包括：

* 接入端点；
* 接入凭证；
* 签名校验；
* 防重放；
* 限流；
* 原始报文保存；
* 协议解析；
* 字段映射；
* 设备识别；
* 业务通道识别；
* 单位转换；
* 失败记录；
* 重试；
* 历史数据重新解析；
* 模拟上报；
* 接入联调；
* 厂家问题定位。

这里的重点不是“支持多少协议”，而是建立一条可靠、可追溯、可扩展的接入链路。

## 4. 时序数据管理

Monitra 的核心数据之一是随时间持续产生的监测值。

系统可能需要支持：

* 实时数据；
* 历史数据；
* 最新接收值；
* 最新有效值；
* 乱序数据；
* 补传数据；
* 重复数据；
* 数据修正；
* 数据版本；
* 统计数据；
* 长期归档；
* 热数据和冷数据分层。

数据不能因为重新上传或重新解析而被无痕覆盖。

如果一条历史数据被修正，系统需要保留：

* 原始版本；
* 修正版本；
* 修正原因；
* 修正人员；
* 修正依据；
* 两个版本之间的关系；
* 哪些下游结果受到影响。

## 5. 数据质量

系统不能默认所有进入平台的数据都是真实、完整和可信的。

Monitra 可能需要识别：

* 重复；
* 缺测；
* 延迟；
* 超量程；
* 异常模式；
* 设备故障；
* 解析失败；
* 绑定错误；
* 时间戳异常；
* 单位转换错误；
* 人工录入问题。

数据质量需要与工程风险分开。

例如：

* 设备故障导致的异常值，不应直接等同于结构发生危险；
* 数据恢复正常，不代表工程风险已经解除；
* 工程监测值恢复，也不代表之前的数据质量问题不需要追踪。

系统需要让用户看见：

* 哪些数据可信；
* 哪些数据可疑；
* 哪些数据无效；
* 判断依据是什么；
* 哪些数据经过人工复核或修正；
* 数据质量问题是否已经恢复。

## 6. 统计与派生计算

原始监测值之外，系统可能需要形成：

* 最大值；
* 最小值；
* 平均值；
* 累计值；
* 变化量；
* 变化速率；
* 标准差；
* RMS；
* 有效率；
* 缺测率；
* 超限次数；
* 多通道差值或组合结果。

其中一部分只是普通统计结果。

另一部分可能形成具有持续业务意义的派生通道。

还有一部分可能形成结构状态或风险判据。

需求文档将结构状态或风险判据类对象称为 FeatureIndicator。

例如：

* 主梁最大挠度；
* 位移变化率；
* 索力偏差率；
* 裂缝增长率；
* 多测点温差；
* 某时间窗口内的振动 RMS；
* 多个通道融合形成的风险指标。

FeatureIndicator 是否应作为系统中的独立核心对象、如何区分普通统计和风险指标，是后续需要重点设计的问题之一。

## 7. 风险判断与告警

* 上限；
* 下限；
* 区间；
* 多级阈值；
* 变化量；
* 变化速率；
* 连续超限；
* 持续超限；
* 恢复阈值；
* 恢复持续时间；
* 数据质量前置条件。

告警不应只是一条消息。

系统可能需要记录：

* 风险来源；
* 命中规则；
* 风险证据；
* 当前严重程度；
* 历史最高严重程度；
* 首次发生时间；
* 最近发生时间；
* 持续命中记录；
* 升级和降级过程；
* 通知情况；
* 专业复核；
* 研判负责人；
* 业主通知；
* 跟踪和反馈过程；
* 恢复过程；
* 授权关闭和归档；
* 最终结论。

系统还需要避免同一个持续风险不断创建大量重复告警。

具体的告警对象、状态、专业研判、通知和反馈流程需要后续结合真实业务进行设计。

## 14. 科研数据与分析

Monitra 可以承载多年连续积累的监测数据，并在项目监测业务之外提供独立的科研数据和分析能力。

科研不从属于某一个 Project。一次科研分析所需的数据可能全部来自一个项目，也可能来自多个项目、多个设施和多个时间范围。原始监测数据仍然归属于各自的项目和权限范围，科研能力通过授权引用这些数据，而不是把数据从原项目中搬走或改变其业务归属。

科研或分析人员可能需要：

* 从一个或多个项目和设施中选择数据；
* 选择监测通道、深度、方向等维度；
* 选择时间范围和采样范围；
* 按数据质量状态过滤数据；
* 添加科研标签和说明；
* 形成固定版本的数据集；
* 选择已经在计算服务中编写并由 Monitra 登记管理的分析算法；
* 配置算法参数并执行计算；
* 查看执行状态、日志和失败原因；
* 保存统计结果、图表、文件和分析结论；
* 将结果引用到科研报告或其他成果中。

这条科研链路可以从以下对象开始理解，但不代表最终对象名称已经确定：

* ResearchDataset 表示经过授权选取、具有固定版本并可重复引用的科研数据集；
* AnalysisAlgorithm 表示计算服务中某个已部署算法在 Monitra 中的可调用登记，包括算法身份、版本、输入参数契约和可用状态，但不包含算法源代码；
* AnalysisRun 表示某个数据集版本使用某个算法版本和一组参数执行的一次分析；
* ResearchResult 表示分析运行产生的统计表、图表、数据文件和结论等结果。

算法不要求预先全部内置。感知中心可以在实际科研需要出现时，在 Monitra 之外、计算服务自己的开发环境中编写、测试和部署算法。计算服务对外暴露已经部署的算法及其输入参数和执行接口，Monitra 再登记或同步算法身份、版本、输入要求、参数定义和可用状态。

Monitra 负责让科研人员能够发现、选择、调用和追踪这些算法，但不是算法开发平台。它不提供算法源代码编辑、代码上传、编译、测试或部署能力，主业务服务也不直接加载和执行算法代码。

系统中的科研数据集不应只是一次查询条件。它需要记录数据来自哪些项目、设施、通道、时间范围和数据版本，以及创建时使用的数据质量过滤条件。即使项目中的原始数据后续发生修正，已经形成并被科研成果引用的数据集版本仍应能够解释和复现。

执行分析时，Monitra 校验数据权限和算法使用权限，创建 AnalysisRun，并将授权数据或受控的数据引用、算法版本和运行参数交给计算服务。计算服务负责执行具体算法，并向 Monitra 返回运行状态、日志、失败信息和结果。Monitra 负责保存数据集版本、算法版本、参数、执行时间、执行状态和结果之间的关系。

算法结果应作为新的分析结果保存，不应无痕覆盖项目中的原始监测数据或业务时序数据。即使算法后续修改或重新部署，历史 AnalysisRun 仍应能够说明当时实际使用的是哪个算法版本。

在感知中心统一平台中，跨项目或跨业主形成科研数据集必须经过独立授权，不能因为用户具备科研职责就自动绕过租户、项目和数据范围。业主级或项目级私有化部署中的科研应用只使用当前部署范围内的数据，除非业主明确授权向外提供。

在产品信息架构上，科研工作空间不应要求用户先进入某一个项目。科研人员应从自己被授权的数据范围出发选择一个或多个项目的数据；当科研能力运行在项目级私有化部署中时，可选范围自然收敛为当前项目。

更复杂的专业健康评价、趋势预测和跨项目智能分析可以在这条可追溯、可复现的科研链路上继续演进。

## 17. 权限和数据边界

Monitra 中的权限不只是“能不能打开一个页面”。

它至少可能包含两个层面：

```text
可以执行什么操作
+
可以访问哪些数据
```

数据范围可能涉及：

* 平台；
* 客户或租户；
* 项目；
* 设施；
* 资产子树；
* 监测通道；
* 特征指标；
* 科研数据集。

同一个人可能在不同项目中承担不同职责，也可能只能查看某个资产或一部分通道。

现有需求文档提出了 User、Identity、Workspace、Role、Permission 和 DataScope 等概念，但这些概念如何组织、用户如何进入系统、是否需要身份选择、是否需要工作台切换，都应在后续身份与权限专题中重新推导。

当前灵感阶段只确认一个原则：

> Monitra 必须能够支持复杂而明确的操作权限和数据范围，但不在此时锁定最终产品形式。

## 18. 部署和运维

Monitra 需要以同一套核心业务模型和产品能力支持三种部署形态。

### 18.1 感知中心统一平台

统一平台部署在中交一公院公司内网，由感知中心使用和运营。

它面向内部工程监测、数据分析、科研和平台运营人员，统一管理多个业主空间、每个业主下的多个监测项目，以及每个项目中的一个或多个基础设施。

```text
感知中心统一平台
├── 业主空间 A
│   ├── 监测项目 A1
│   │   ├── 基础设施 A1-1
│   │   └── 基础设施 A1-2
│   └── 监测项目 A2
└── 业主空间 B
```

这种形态在技术上具有多租户 SaaS 的特征，但产品上更接近服务于感知中心内部业务的中心平台。

### 18.2 业主级私有化部署

业主级私有化部署安装在业主自己的服务器或内网中，只服务一个固定业主，但可以管理该业主的多个监测项目。

```text
业主级私有化部署
└── 固定业主
    ├── 监测项目 A
    ├── 监测项目 B
    └── 监测项目 C
```

在这种形态中，业主范围已经由部署确定，普通用户不需要选择或管理租户。产品界面可以直接从业主范围内的项目管理和监测业务开始。

### 18.3 项目级私有化部署

项目级私有化部署同样安装在业主自己的服务器或内网中，但只服务一个固定监测项目。一个项目仍然可以包含多座桥梁或其他多个基础设施。

```text
项目级私有化部署
└── 固定监测项目
    ├── 基础设施 A
    ├── 基础设施 B
    └── 基础设施 C
```

在这种形态中，用户登录后可以直接进入项目业务，不必经过没有实际选择意义的业主选择或项目选择。

三种形态不应演变成三套相互分叉的产品。它们应共享核心领域模型、数据结构和业务能力，主要区别是可管理范围、管理入口、导航层级和可见的管理功能：

* 感知中心统一平台允许多个业主空间和多个项目；
* 业主级私有化部署固定业主范围，允许多个项目；
* 项目级私有化部署同时固定业主和项目范围；
* 三种形态都允许一个项目包含一个或多个基础设施；
* 感知中心统一平台和业主级私有化部署可以识别同一设施先后或同时关联的多个项目，并在授权范围内提供跨项目历史关联；
* 项目级私有化部署只呈现当前项目的监测上下文，不依赖其他项目或其他部署实例才能正常运行；
* 私有化部署独立运行，不依赖感知中心统一平台在线提供身份、配置、授权或数据服务；
* 公共指标、设备协议、监测模板和报告模板等平台能力，可以通过明确版本的安装包或升级包交付给私有化部署，而不是运行时继承中心平台状态。

Monitra 还需要适应离线安装、不同规模项目和未来可能出现的现场边缘环境。

系统可能由多个运行部分组成，例如：

* 面向用户的业务服务；
* 设备数据接入服务；
* 后台任务服务；
* 协议解析服务；
* 时序数据存储；
* 消息系统；
* 缓存；
* 对象存储；
* 计算服务；
* 日志、指标和链路追踪。

其中，计算服务用于承载按科研需要编写的算法及其执行环境。Monitra 主业务服务不直接加载算法代码，而是通过明确的任务和结果契约调用计算服务。启用科研计算能力的业主级或项目级私有化部署，需要在本地部署可独立运行的计算服务，不能依赖感知中心内网中的计算服务才能完成分析。

从产品角度看，运维人员需要知道：

* 服务是否正常；
* 数据是否持续进入；
* 哪个链路发生积压；
* 哪些报文解析失败；
* 时序数据是否正常写入；
* 最新值是否正常更新；
* 风险计算是否正常；
* 通知是否成功；
* 备份是否完成；
* 是否能够恢复；
* 当前系统运行的是哪个版本。

Monitra 不只是能够部署，还需要具备长期稳定运行、故障定位、备份恢复和升级交付能力。

## 六、Monitra 最重要的业务链路灵感

## 1. 项目实施与初始化链路

```text
建立项目
→ 描述真实参与单位
→ 配置项目人员和访问范围
→ 建立设施和资产结构
→ 建立监测位置
→ 配置监测指标和业务通道
→ 配置设备和数据来源
→ 建立设备字段与业务通道关系
→ 联调并验证数据
→ 配置风险判断
→ 配置报告和展示
→ 正式运行
```

## 2. 设备数据链路

```text
设备、网关、文件、人工或第三方系统产生数据
→ 完成接入鉴权
→ 保存原始信息
→ 解析数据格式
→ 识别设备与原始字段
→ 找到对应业务监测通道
→ 执行单位或数值转换
→ 判断数据质量
→ 写入时序数据
→ 更新最新状态
→ 进入统计、风险和展示能力
```

## 3. 数据质量链路

```text
接收监测数据
→ 执行质量规则
→ 形成有效、可疑或无效结论
→ 保存原因和证据
→ 影响最新有效值和后续计算
→ 形成质量问题
→ 人工复核或修正
→ 保存新版本
→ 保留全部历史
```

## 4. 风险判断链路

```text
有效监测数据
→ 基础统计或特征计算
→ 风险规则判断
→ 形成告警事件
→ 记录触发证据
→ 专业人员复核
→ 通知业主或相关人员
→ 记录跟踪过程和外部反馈
→ 持续判断告警条件
→ 记录条件恢复
→ 经授权关闭和归档
```

## 5. 报告与成果链路

```text
选择项目、设施、通道和时间范围
→ 聚合数据、统计、风险、设备和质量信息
→ 生成报告内容
→ 补充专业分析
→ 审核与发布
→ 形成正式版本
→ 输出文件
→ 归档到成果体系
```

## 6. 数据追溯链路

```text
报告或告警中的一个结论
→ 找到引用的数据或计算结果
→ 找到对应时序数据版本
→ 找到数据质量评价
→ 找到设备字段和绑定关系
→ 找到解析结果
→ 找到原始报文
→ 找到当时使用的规则和配置版本
```

这条反向追溯能力，是 Monitra 建立可信监测体系的基础。

## 7. 科研分析链路

```text
一个或多个项目持续产生监测数据
→ 按授权选择设施、通道、时间范围和数据质量条件
→ 形成固定版本的 ResearchDataset
→ 在 Monitra 之外按需编写、测试并向计算服务部署算法
→ Monitra 登记或同步可调用的 AnalysisAlgorithm
→ 选择具体算法版本
→ 配置参数并创建 AnalysisRun
→ Monitra 将授权数据和参数交给计算服务
→ 计算服务执行统计或分析计算
→ Monitra 接收运行状态、日志和结果
→ 形成可追溯的 ResearchResult
→ 引用到科研报告或其他成果
```

这条链路独立于单个项目，但其中每一项输入数据都必须能够追溯到原项目、业务通道和数据版本，每一项结果也必须能够追溯到使用的数据集版本、算法版本、运行参数和计算服务执行记录。

## 七、一个典型的 Monitra 业务故事

某项目需要对一座桥梁进行长期健康监测。

项目团队首先在 Monitra 中建立项目，描述桥梁结构、参与单位和监测目标。

随后建立桥梁的设施结构，配置主梁、桥墩、支座和监测断面，并在相应位置建立位移、应变、温度和振动监测对象。

设备人员录入设备厂家、产品型号和具体设备，将设备上传字段与业务监测通道建立关系。

设备通过 MQTT 或其他方式持续上报。

Monitra 保存原始报文，执行协议解析、设备识别、通道匹配和数据质量评价，最终形成连续的业务时序数据。

某一天，一个设备上传了明显异常的数据。

系统发现该数据可能由设备故障导致，因此先形成数据质量问题，而不是立即认定桥梁出现工程风险。

设备恢复后，后续有效数据继续进入。

之后，系统根据多个位移通道计算主梁位移变化率。该指标持续超过预设风险范围，系统形成风险告警，并保存对应数据、计算结果和阈值证据。

专业人员收到通知，查看风险位置、历史趋势和数据质量，完成初步复核并向业主通知。业主根据自身职责决定是否组织现场检查或采取其他措施。

项目人员可以在 Monitra 中记录业主或现场反馈，也可以关联由外部系统形成的检查记录和措施证据。

即使业主反馈已经完成现场检查或采取外部措施，只要监测条件仍然处于超限状态，系统仍然保留告警活动状态。

直到数据真实回到恢复范围并持续一定时间，系统才记录告警条件恢复。条件恢复不自动等同于工程风险已经解除，告警是否关闭仍需由具备权限的人员结合专业研判和反馈信息确认。

项目人员最后基于整个过程生成告警研判与跟踪报告。报告中引用相关曲线、风险证据、通知记录、业主或现场反馈和恢复过程，并作为正式成果归档。

这个故事体现了 Monitra 希望形成的完整关系：

```text
现实工程
→ 设备和数据
→ 数据可信度
→ 风险判断
→ 专业研判和业主反馈
→ 恢复证据
→ 正式成果
```

## 八、Monitra 的平台化想象

Monitra 的长期价值不只在于完成一个项目。

每一个项目中形成的新内容，都有机会沉淀为平台能力：

* 一种新的设施类型；
* 一套新的资产结构；
* 一种新的监测指标；
* 一种新的设备产品；
* 一个新的设备协议；
* 一套新的通道模板；
* 一种新的数据质量规则；
* 一个新的风险判据；
* 一套新的报告模板；
* 一种新的可视化形式；
* 一套新的外部编码映射；
* 一种新的项目初始化方案。

这样，下一次遇到类似项目时，就不需要重新开发，而可以从已有能力出发进行配置和调整。

Monitra 希望逐步形成交通基础设施监测行业中的可复用数字能力库。

## 十、后续需要由 AI 带领逐步设计的问题

当前阶段不急于给出最终答案，而应以 Monitra 的业务目标为基础，一轮一轮完成以下问题。

### 1. 产品边界

* Monitra 最核心、不可缺少的业务闭环是什么？
* 哪些能力属于核心产品？
* 哪些能力只是项目交付工具？
* 哪些能力属于远期演进？
* 哪些内容虽然出现在需求文档中，但实际上不应该进入产品？

当前已经确认：Monitra 面向交通基础设施运营期健康监测、长期性能观测和科研应用，不覆盖建设期监测，也不承载业主的养护计划、维修工程和养护验收等养护业务。

### 2. 用户与业务场景

* 系统中真实存在什么类型的用户？
* 每类用户进入系统是为了完成什么工作？
* 哪些用户长期使用，哪些用户偶尔查看？
* 哪些用户负责配置，哪些用户负责监测，哪些用户负责专业研判、通知和跟踪？
* 一个用户存在多个身份时，最自然的使用方式是什么？

### 3. 系统信息架构

* 系统应该按照项目、职责、业务链路还是对象组织？
* 是否需要工作台？
* 如果需要，工作台应该如何自然形成？
* 哪些业务应该聚合，哪些业务应该拆分？
* 怎样避免把系统设计成数据库表对应的 CRUD 后台？

### 4. 项目实施与初始化过程

* 一个新项目如何从零开始建立？
* 哪些步骤有严格依赖关系？
* 哪些步骤可以并行？
* 如何让实施人员随时知道项目还缺什么？
* 模板和批量配置应该发挥多大作用？

### 5. 核心业务对象

* Project、Asset、MonitoringPoint、MonitorChannel、Device 和 FeatureIndicator 的边界是否合理？
* 哪些概念需要保留？
* 哪些概念过于复杂？
* 哪些对象应该成为用户能够直接理解和操作的一等对象？
* 哪些对象只应该存在于系统内部？

当前已经确认：Project 是一次运营期监测业务和交付的主要上下文，可以包含一个或多个 Facility；Facility 表示稳定的现实设施身份，可以被续约合同或新的运营监测任务形成的新 Project 继续关联。项目之间不会因为关联同一 Facility 就自动共享数据和权限。

科研不属于 Project。科研能力通过 ResearchDataset 在独立授权下引用一个或多个项目的监测数据。算法在 Monitra 之外完成编写、测试和部署；Monitra 只管理已部署 AnalysisAlgorithm 的可调用登记、版本、权限和可用状态，并创建和跟踪 AnalysisRun；独立计算服务管理算法实现和执行环境，并将运行状态、日志和结果返回 Monitra，最终形成可追溯、可复现的 ResearchResult。

### 6. 设备接入与数据可信

* 设备接入应该如何让非技术人员也能理解？
* 原始报文、解析结果和业务数据怎样建立清楚关系？
* 数据质量如何呈现，才能帮助工程人员判断而不是制造更多复杂度？
* 数据修正、重放和版本追溯需要做到什么程度？

### 7. 风险、研判与反馈

* 什么是告警，什么是数据质量问题，什么是设备故障？
* 风险如何从数据产生？
* 哪些风险需要人工确认？
* 告警的生命周期如何符合监测单位的专业复核、业主通知、跟踪和反馈过程？
* 哪些状态由 Monitra 管理，哪些检查、管制、维修或其他措施只记录外部反馈而不在 Monitra 中执行？
* 如何防止系统产生大量无意义或重复告警？

### 8. 报告与成果

* 报告是系统自动生成，还是辅助工程师编制？
* 哪些内容必须结构化？
* 报告审核和版本管理需要多复杂？
* 项目最终需要交付什么成果？
* 成果中心应解决什么核心问题？

### 9. 可视化与空间能力

* GIS、图表、大屏和三维模型分别解决什么问题？
* 哪些场景真正需要三维？
* 日常业务界面和展示大屏应该如何复用能力？
* 如何防止展示能力喧宾夺主，掩盖核心业务？

### 10. 产品形态与部署

当前已经确认 Monitra 支持感知中心统一平台、业主级私有化和项目级私有化三种形态。三种形态共享核心业务模型和产品能力，通过固定或放开业主、项目范围形成不同体验。

后续仍需继续设计：

* 不同形态分别显示或隐藏哪些管理入口？
* 用户登录后如何直接进入对其有意义的业务范围？
* 哪些差异属于范围约束，哪些差异需要正式的产品能力开关？
* 私有化部署如何离线安装、升级、备份、恢复和接收版本化模板？
* 如何防止三种形态形成三套代码、三套数据模型或大量条件分支？

### 11. 实施与演进

* 如何从完整愿景中找到最先能够运行的业务闭环？
* 每次迭代应该交付什么可见成果？
* 如何保证快速看到效果，又不使用临时模型和一次性代码？
* 如何让新项目持续沉淀为平台能力？

## 十一、当前阶段的一句话定义

Monitra 是一套试图将交通基础设施运营期监测项目、设施、监测对象、设备、数据、质量、风险、专业研判、反馈和交付成果连接起来，并支持长期科研应用的行业级监测软件。

它的目标不是提前规定所有页面和操作方式，而是建立一个足够完整的业务世界，随后围绕真实用户和真实业务链路，逐步推导出最合适的产品结构。

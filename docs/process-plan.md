# Monitra 滚动式设计与推进计划

## 一、这份计划的定位

Monitra 当前唯一的产品愿景权威文档是：

```text
docs/inspire.md
```

`inspire.md` 描述 Monitra 面对的业务世界、长期目标、已经确认的原则和仍待设计的问题。

本文件不重新定义产品，也不提前替 `inspire.md` 回答尚未回答的问题。

本文件只规定：

```text
怎样看见整个系统向前生长；
怎样选择当前最值得推进的一小段；
怎样先完成必要设计；
怎样把当前设计拆成足够小的实现单元；
怎样通过运行证据确认系统真的向前推进；
怎样把新确认的事实和决策沉淀下来；
怎样在不预先虚构远期细节的情况下持续推进到完整系统。
```

如果本计划与 `inspire.md` 冲突，以 `inspire.md` 为准，并调整本计划。

如果实施中发现 `inspire.md` 内部存在矛盾、缺少关键边界，或者真实业务证据要求改变其中已经确认的原则，必须先和用户完成产品决策，再更新 `inspire.md`。不得由实现代码、数据库结构或某张 Ticket 暗中替产品做决定。

---

## 二、当前文档的权威关系

当前阶段，文档按以下关系工作：

```text
inspire.md
    │
    │  唯一产品愿景来源
    │
    ├── process-plan.md
    │       只规定推进方法，不增加产品事实
    │
    ├── CONTEXT.md
    │       逐步记录已经确认的领域术语和边界
    │
    ├── docs/adr/*.md
    │       逐步记录已经明确作出的重要设计决策
    │
    ├── 当前推进单元的 Spec
    │       只描述当前已经完成设计的范围
    │
    └── 当前推进单元的 Ticket
            只描述当前已经可以直接实现的行为
```

其中，`CONTEXT.md`、ADR、Spec 和 Ticket 目前都不是预先存在的产品权威。

它们只有在相关问题已经根据 `inspire.md`、真实业务案例和用户确认完成设计后，才开始记录已经确认的结论。

它们必须满足：

* 不与 `inspire.md` 冲突；
* 只约束自己明确覆盖的范围；
* 不把未决定的问题写成确定事实；
* 不因为代码已经这样实现，就反过来把实现当成产品决定；
* 当产品原则发生变化时，先更新上游权威，再调整下游文档和实现。

当前实施资料统一放在本地 Markdown Tracker 中：

```text
.scratch/<当前推进主题>/spec.md
.scratch/<当前推进主题>/issues/<NN>-<slug>.md
```

长期稳定的领域术语和架构决策不放在临时 Ticket 中，分别沉淀到 `CONTEXT.md` 和 `docs/adr/`。

## 三、整个 Monitra 向前推进的全景

Monitra 不是按菜单、数据库表或技术组件逐块堆出来的。

它应当沿着 `inspire.md` 中已经形成的完整业务关系逐步生长。

## 1. 业务主干全景

```text
现实业务范围与项目上下文（以下概念不表示固定层级）
│
├── Organization / TenantSpace / Deployment
├── Project / Facility
└── 项目参与关系、人员和访问范围
        │
        ▼
设施与监测对象
│
├── Facility 与项目监测上下文
├── Asset 或设施结构
├── MonitoringPoint
├── Indicator
└── MonitorChannel
        │
        ▼
数据来源与接入
│
├── 人工录入、文件导入和历史迁移
├── 设备厂家、产品和设备实例
├── 设备字段或原始通道
├── 接入端点和凭证
├── RawMessage
└── 解析、设备识别、绑定和转换
        │
        ▼
可信监测数据
│
├── 业务观测值和时序数据
├── 观测时间、接收时间和来源
├── 重复、乱序和补传
├── 数据质量结论和证据
├── latest_received / latest_valid
└── 人工复核、修正和版本关系
        │
        ▼
计算与风险发现
│
├── 统计结果
├── 派生结果或 FeatureIndicator
├── 风险规则和规则版本
├── Alarm / Occurrence
└── 风险证据、条件恢复和状态变化
        │
        ▼
专业研判、通知与反馈
│
├── 专业人员复核
├── 负责人和待处理事项
├── 相关人员或业主通知
├── 外部现场检查与措施反馈
├── 处置和证据记录
└── 经授权关闭和归档
        │
        ▼
报告、成果与长期数据资产
│
├── 报告草稿、审核、发布和版本
├── 数据导出、汇交和成果包
├── 结论到原始证据的反向追溯
├── ResearchDataset / DatasetVersion
├── AnalysisAlgorithm / AnalysisRun
└── ResearchResult
```

这条业务主干给出的是因果关系和系统生长方向，不是预先锁定的版本顺序。

例如，科研能力需要可信数据、版本追溯、数据权限和多项目选择作为前提，因此不会仅因为它出现在全景中，就被提前分配到某个固定版本。

## 2. 贯穿所有业务能力的横向基础

业务主干每向前推进一段，下面这些基础也要同步深化：

```text
身份与数据边界
├── 稳定用户身份
├── 当前可访问范围
├── 操作权限
└── 授权与访问审计

证据与版本追溯
├── 来源身份
├── 发生时间和接收时间
├── 配置、绑定、规则和算法版本
├── 状态变化原因
└── 结论到原始证据的反向关系

运行与数据安全
├── 健康状态
├── 结构化日志和 request_id
├── 指标和链路追踪
├── 失败状态、重试和补偿
├── 数据库迁移
├── 备份与恢复
└── 升级与回滚

产品复用与部署边界
├── 感知中心统一平台
├── 业主级私有化
├── 项目级私有化
├── 模板和批量配置
├── 离线安装和升级包
└── 能力启停和部署范围
```

这些不是最后再补的独立版本。

它们从第一条真实业务数据、第一次真实用户操作和第一次可部署运行开始出现，然后随着业务风险逐步深化。

## 3. 展示、空间、科研和开放能力的位置

GIS、三维、科研、开放接口、大屏、移动端、视频、边缘和 AI 都属于 `inspire.md` 描述的系统全景。

但它们是否进入某一次近期交付、进入到什么深度，要由真实用户价值和已经具备的前置能力决定。

它们不自动成为核心主干的固定下一步，也不因为暂时没有实现就从全景中消失。

可以把它们理解为从主干上长出的能力分支：

```text
可信监测数据 ───────→ GIS、图表和项目态势
监测对象与空间关系 ─→ 三维模型与业务锚点
长期可信数据 ───────→ ResearchDataset 和分析计算
稳定权限与数据契约 ─→ 外部应用和监管汇交
稳定任务与证据链 ──→ 移动现场协同
可信数据和人工确认 ─→ AI 与知识能力
```

分支能力只有在其依赖已经具备、真实使用场景已经确认时，才进入当前设计前沿。

## 四、用三种视野同时管理推进

Monitra 采用滚动规划，而不是一次性写完从 V0.0 到 V1.0 的所有详细版本。

任何时候都同时保留三种视野。

## 1. 全景视野

全景视野回答：

```text
完整系统最终要连接哪些业务环节？
当前已经走到了哪里？
哪些能力已经形成真实闭环？
哪些能力只有模型，还没有上下游消费者？
哪些横向基础已经跟上，哪些仍然不足？
哪些分支能力还在等待真实价值和前置条件？
```

全景视野使用能力地图和证据台账表达，不写远期详细 Ticket。

## 2. 近景视野

近景视野只看接下来可能推进的一到两个业务结果。

它记录：

* 候选用户结果；
* 为什么它是当前自然的下一步；
* 它依赖哪些已有能力；
* 还存在哪些产品或领域问题；
* 需要什么真实案例或技术验证；
* 哪些问题不解决就不能进入实现。

近景候选不是承诺，不提前拆 Ticket。

## 3. 当前前沿视野

当前前沿是唯一允许被详细设计和拆成实现 Ticket 的范围。

它必须足够小，使用户和 Codex 能够：

* 看见一个明确问题；
* 一次确认一个重要设计决策；
* 在短时间内形成真实运行结果；
* 解释结果如何连接已有系统；
* 明确它让整个业务主干向前移动了哪一小步。

当前前沿完成后，重新观察全景，再选择下一前沿。

不得因为曾经写过一张长期路线表，就机械进入下一个预定版本。

## 五、版本如何在滚动推进中产生

版本不再是预先铺满整条路线的计划单位。

它是当前前沿经过设计以后，为一个完整、可验收用户结果建立的交付边界。

关系如下：

```text
系统全景
└── 当前前沿
    └── 当前交付切片
        ├── 决策推进单元
        ├── 行为推进单元
        └── 证据推进单元
```

只有当前交付切片满足以下条件时，才给它建立版本章程或里程碑：

* 用户结果已经明确；
* 阻塞实现的产品决策已经完成；
* 与已有系统的连接位置已经确认；
* 范围内和范围外已经明确；
* 能够拆成少量可独立验收的推进单元；
* 当前结果所需的权限、追溯、失败和运行要求已经明确。

任何时候只允许：

```text
当前交付切片：具有完整 Spec、Ticket 和验收；
下一候选切片：只有候选结果、依赖和待决问题；
更远能力：只存在于全景和能力证据台账中。
```

因此，版本号不承担预测未来设计细节的职责。

如果一个当前交付切片完成后暴露出新的事实，下一版本根据新事实重新设计；不需要服从旧文档中曾经猜测的编号和步骤。

## 六、最小推进粒度

计划不再把“一个版本”当作最小思考单位。

Monitra 的最小推进单位称为“推进单元”。

一个推进单元只消除一个明确的不确定性，或者只交付一个明确的可验收行为。

## 1. 决策推进单元

决策推进单元一次只回答一个会影响实现方向的问题。

例如：

```text
Facility 的稳定身份是否只在一个 Deployment 内成立？

Project 与 Facility 之间是否需要独立的项目监测上下文？

一条人工观测值必须记录哪些来源和时间信息？

数据质量结论是 Observation 的状态，还是一份可版本化的独立评价？

告警的“条件恢复”和“人工关闭”分别是什么事件？
```

一个决策推进单元必须包含：

* 来自 `inspire.md` 的相关原则；
* 当前代码和数据结构的事实；
* 一个真实业务案例；
* 仍未确定的单一问题；
* 可选方案及其影响；
* 用户确认的结论；
* 需要更新的领域文档或 ADR。

如果问题还没有答案，就保持为待决问题，不进入实现 Ticket。

## 2. 行为推进单元

行为推进单元只交付一个用户行为或一个系统反应。

例如：

```text
用户可以看到一个项目关联的设施名称。

用户向一个 MonitorChannel 提交一条带观测时间的人工观测值。

系统拒绝一条引用不存在 MonitorChannel 的观测值。

重复提交同一个原始报文时，系统不产生第二条业务观测值。

一条无效数据不会覆盖 latest_valid。

一个持续超限只追加 Occurrence，不创建第二个活动 Alarm。
```

一个行为推进单元通常具有：

* 一个主要参与者或调用方；
* 一个主要输入；
* 一个主要业务判断；
* 一个主要状态变化或输出；
* 一个清晰失败分支；
* 一到三个核心自动测试；
* 一个可运行的演示方法。

“一个行为”比“一个领域对象”更重要。

如果证明一个行为必须同时建立两个紧密相关的概念，可以在同一个推进单元中引入它们。不得为了机械满足“一个 Ticket 一个概念”，制造只有表、没有消费者的孤立对象。

## 3. 证据推进单元

有些推进单元不增加新的用户功能，而是证明已有能力在真实条件下成立。

例如：

```text
进程重启后，已经提交的观测值仍然存在。

数据库恢复后，告警和其证据关系保持完整。

设备补传乱序数据时，latest_valid 仍然正确。

未授权用户无法通过直接调用 API 读取项目数据。

一份已发布报告仍然引用发布时的数据版本。
```

证据推进单元用于补充可靠性、安全、追溯、运维和性能，不允许全部推迟到最终集成阶段。

## 4. 推进单元的规模警戒线

以下是默认检查项，不是机械限制：

* 能否用一句话说明唯一主要结果；
* 是否只解决一个决策问题或一个行为；
* 是否有一个可以故意触发的失败分支；
* 是否能独立运行和验收；
* 是否会留下没有消费者的对象；
* 是否偷偷决定了当前尚未确认的产品边界；
* 是否需要用户在十分钟以上才能讲清完整调用链；
* 是否包含两个可以独立交付、独立失败的状态变化；
* 是否修改了过多业务文件或引入了多个无关迁移。

如果一个单元过大，优先按行为和状态变化拆分，而不是按 Controller、Service、Repository 或数据库表分层拆分。

## 七、每一轮如何边设计边推进

每一轮只推进一个当前前沿，并采用以下闭环。

## 阶段 0：重新观察系统事实

开始前先检查：

* 当前仓库、分支和工作区状态；
* 已经存在的代码、测试和运行方式；
* `inspire.md` 中与当前主题相关的内容；
* 已经确认的领域术语和 ADR；
* 上一个推进单元的验收证据和遗留问题；
* 能力地图中当前主干已经走到的位置。

历史计划不能替代当前事实。

## 阶段 1：选择下一个最小业务结果

选择标准依次是：

1. 是否直接推动 `inspire.md` 中的核心业务关系；
2. 是否让已有对象出现真实上下游消费者；
3. 是否尽早暴露高成本领域错误；
4. 是否建立后续多项能力共同依赖的稳定边界；
5. 是否能形成真实、可运行、可解释的结果；
6. 是否避免提前进入尚无真实价值的分支能力。

选择后只写候选用户结果，不立即写代码和 Ticket。

## 阶段 2：列出当前阻塞设计的问题

围绕候选用户结果，列出：

* 参与者是谁；
* 他为什么执行这个行为；
* 涉及哪些业务对象；
* 哪些术语已经确认；
* 哪些边界仍不清楚；
* 哪些规则影响数据结构或长期追溯；
* 哪些权限、部署、审计和失败语义从一开始就必须存在；
* 需要哪个真实项目案例才能判断。

只把会改变当前实现方向的问题视为阻塞问题。

远期问题继续保留在全景中，不为了当前推进而一次性设计完整系统。

## 阶段 3：一次完成一个设计决策

对每个阻塞问题依次进行：

```text
查阅 inspire.md
→ 查看当前代码和已有决策
→ 引入一个真实业务案例
→ 明确一个问题
→ 比较可选方案
→ 用户确认
→ 记录结论
```

一次只确认一个真正影响方向的决策。

如果缺少事实，可以先建立研究或原型推进单元；不得用猜测填满 Spec。

## 阶段 4：形成当前前沿 Spec

只有阻塞当前实现的产品问题已经解决，才创建：

```text
.scratch/<frontier>/spec.md
```

当前前沿 Spec 只包含：

```markdown
# 当前前沿

## 它推动全景中的哪一段

## 真实参与者和业务场景

## 当前用户结果

## 已确认术语和边界

## 业务规则和不变量

## 输入、状态变化和输出

## 失败与拒绝行为

## 权限、追溯和运行要求

## 明确不做

## 验收证据

## 不阻塞当前推进的待决问题
```

Spec 中不得包含仍需要用户决定的关键产品问题。

## 阶段 5：只拆当前前沿的推进单元

把当前 Spec 拆成少量 Ticket：

```text
.scratch/<frontier>/issues/<NN>-<slug>.md
```

每张 Ticket 采用：

```markdown
# 一个决策或一个行为

Type: decision | implementation | evidence | research | prototype
Status: needs-triage | ready-for-agent | ready-for-human | resolved

## 它让系统向前移动什么

## 当前事实和调用链

## 唯一主要结果

## 输入和前置状态

## 业务规则或待决问题

## 成功后的状态变化

## 失败或拒绝行为

## 预计修改范围

## 自动测试

## 运行演示

## 明确不做

## 完成证据
```

只创建当前前沿所需的 Ticket。

下一前沿即使看起来明显，也只保留候选结果和待决问题，不提前拆详细步骤。

## 阶段 6：按可执行顺序实现

一个实现推进单元采用：

```text
理解当前调用链
→ 明确验收行为
→ 先建立失败测试或可重复验收
→ 最小正式实现
→ 运行相关测试
→ 在真实进程和正式存储上演示
→ 解释入口、规则、状态和证据
```

最小实现不等于临时代码。

不得为了快速通过当前 Ticket：

* 建立未来必然废弃的第二套领域模型；
* 使用长期存在的假数据替代正式链路；
* 绕过身份和数据范围；
* 无痕覆盖原始数据或历史状态；
* 省略当前行为必需的来源、时间和版本信息；
* 只实现数据库表或 API，而没有真实调用者；
* 提前建立没有当前消费者的平台抽象。

## 阶段 7：用多类证据完成验收

一个前沿完成时，至少从下面几类证据中选择相关项：

### 用户结果证据

真实用户行为可以被演示，成功和失败都清楚可见。

### 生产代码证据

能够指出请求入口、业务规则、状态变化、持久化和返回结果的位置。

### 数据证据

能够说明正式记录如何保存、如何关联、如何查询以及是否会被无痕覆盖。

### 追溯证据

能够从结果找到来源、版本、规则、操作者或原始输入。

### 安全证据

能够证明未认证、未授权或超出数据范围的请求被后端拒绝。

### 失败与恢复证据

能够证明重复、重启、部分失败、补传或恢复场景不会破坏业务事实。

### 运行证据

能够观察服务、关键链路、失败状态、备份和当前版本。

不是每个最小 Ticket 都需要覆盖全部七类，但当前行为产生的风险必须在同一前沿内得到对应证据。

## 阶段 8：回写全景并重新选择前沿

完成后更新：

* 当前能力已经达到什么状态；
* 哪个真实用户结果已经成立；
* 哪些领域术语或决策已经确认；
* 哪些上下游关系已经被实际证明；
* 哪些横向基础已经同步深化；
* 暴露了哪些新的待决问题；
* 原来的近景候选是否仍然是自然下一步。

然后重新选择，而不是自动执行旧路线中的下一编号。

## 八、能力如何在全景中表示

为了看见整个系统不断前进，可以维护派生的能力证据台账：

```text
docs/product/CAPABILITY_COVERAGE.md
```

它不是新的产品需求来源，只是 `inspire.md` 与当前运行事实之间的导航图。

每项能力至少记录：

| 字段 | 含义 |
| --- | --- |
| 能力 | 来自 `inspire.md` 的业务能力或关系 |
| 上游依赖 | 当前能力成立前必须具备什么 |
| 下游去向 | 当前能力会被谁使用 |
| 当前状态 | 还处于问题、设计、实现还是已验证状态 |
| 证据 | Spec、代码、测试、演示或运行证据 |
| 待决问题 | 仍未确认但不伪装成事实的问题 |
| 候选下一深化 | 当前自然可能继续推进的方向 |

能力状态采用：

```text
愿景中存在
→ 正在设计
→ 最小实现
→ 单链路可用
→ 主链路闭环
→ 生产深化
→ 综合验收
```

状态必须由证据支撑。

“存在一张表”不能证明能力已经实现；“测试是绿色的”也不能单独证明真实业务闭环已经成立。

同一个业务概念允许具有写模型、查询投影、缓存和最新值物化结果，但必须明确：

* 哪一个是业务事实来源；
* 哪些只是派生状态；
* 派生状态如何重建；
* 失败时如何发现不一致；
* 不允许出现两个互不知晓的业务事实来源。

## 九、系统生长时应优先验证的依赖关系

下面给出全系统的主要依赖方向，用于形成全景想象，不代表已经决定详细版本。

## 1. 监测业务成立之前

至少需要逐步确认：

```text
第一个真实使用者和业务场景
→ 第一个目标部署范围
→ Project 与 Facility 的关系
→ 设施结构和 MonitoringPoint 的最小边界
→ Indicator 与 MonitorChannel 的最小关系
→ 用户身份和当前数据范围
```

## 2. 第一条正式观测值成立之前

至少需要逐步确认：

```text
业务通道身份
→ 观测时间与接收时间
→ 数值、单位和精度
→ 数据来源和操作者
→ 初始质量语义
→ 重复与幂等语义
→ 正式存储和重启后可恢复
```

## 3. 第一条设备数据成立之前

至少需要逐步确认：

```text
设备、设备字段与 MonitorChannel 的边界
→ 绑定的生效时间和版本
→ 原始报文保存
→ 接入鉴权
→ 解析规则和转换版本
→ 重复、乱序、补传和失败状态
→ 从业务数据反向找到原始报文
```

## 4. 第一条可信数据成立之前

至少需要逐步确认：

```text
有效、可疑、无效和未评价的含义
→ 质量规则和证据
→ latest_received 与 latest_valid
→ 人工复核
→ 修正版本和修正理由
→ 哪些下游结果需要失效或重算
```

## 5. 第一条工程风险成立之前

至少需要逐步确认：

```text
数据质量前置条件
→ 统计、派生结果或 FeatureIndicator 的边界
→ 风险规则和规则版本
→ 告警去重和 Occurrence
→ 升级、降级和条件恢复
→ 风险证据反向追溯
```

## 6. 第一条人员闭环成立之前

至少需要逐步确认：

```text
专业复核责任
→ 通知对象和通知证据
→ 研判、分派和跟踪
→ 外部检查或措施反馈
→ 条件恢复与人工关闭的区别
→ 关闭权限、最终结论和完整时间线
```

## 7. 第一份正式成果成立之前

至少需要逐步确认：

```text
成果使用的数据和时间范围
→ 数据、统计、告警和反馈的明确版本
→ 人工专业结论
→ 审核、发布和归档
→ 发布后不可无痕变化
→ 从成果反向追溯到原始证据
```

## 8. 多项目、科研和平台化成立之前

至少需要逐步确认：

```text
稳定的单项目业务闭环
→ Organization / TenantSpace / Project / Facility 边界
→ 参与关系与访问授权分离
→ 多项目数据隔离
→ 跨项目独立授权
→ 数据集、算法和运行版本
→ 三种部署形态的固定范围与独立运行
→ 模板、升级包和开放契约
```

这些依赖关系使团队能看见完整系统如何长出来，同时避免提前为每一个远期能力编写未经设计的版本和 Ticket。

## 十、当前真正应该开始的推进前沿

当前不能直接把旧计划中的 `V0.0 / S0.0.1` 当作完整产品路线的既定第一张 Ticket。

技术运行基线可以建立，但第一条业务实现之前需要先完成一个很小的设计前沿。

当前前沿暂定为：

```text
确定 Monitra 第一条真实、可信、可演示的业务闭环边界。
```

它不是要求现在设计完整系统，而是依次确认：

1. 选择一个真实试点场景，而不是抽象的“演示项目”；
2. 明确第一个真实使用者及其要完成的动作；
3. 明确这个动作推动业务主干中的哪一段；
4. 只确认支撑该动作所需的最小领域对象和不变量；
5. 明确第一条结果必须携带的来源、时间、权限和追溯信息；
6. 明确成功、拒绝、重启后恢复等验收行为；
7. 完成这些设计后，再生成第一份当前前沿 Spec 和少量 Ticket。

与此同时，可以建立不替产品做决定的工程事实基线，例如：

* 仓库可回退基线；
* 后端和前端的正式入口；
* 测试运行方式；
* liveness 与 readiness；
* 数据库迁移机制；
* 结构化日志和 request_id；
* 一条命令启动；
* 第一份持久数据出现前的备份与恢复方法。

第一条业务闭环具体是“人工观测”“项目与设施展示”还是其他行为，不在本计划中提前决定。

它必须从 `inspire.md`、真实项目案例和用户确认中产生。

## 十一、一个当前前沿可能如何被细化

下面只是说明粒度，不是已经批准的 Monitra 版本或 Ticket。

假设未来确认第一条业务结果是：

```text
一个已认证用户，可以在被授权的项目中，
向一个 MonitorChannel 提交一条人工观测值，
并看到最新值和历史记录。
```

它不会直接作为一张大 Ticket，而会先出现决策推进单元：

```text
D01：确认该项目如何关联 Facility。
D02：确认 Facility、Asset 与 MonitoringPoint 的当前最小边界。
D03：确认 MonitorChannel 的最小稳定身份。
D04：确认人工观测值必须保存的时间、来源、单位和操作者。
D05：确认当前最小 ProjectScope 如何保护业务 API。
```

只有这些问题得到回答，才可能形成行为推进单元：

```text
I01：已认证用户可以读取被授权项目的名称。
I02：项目页面可以显示其设施和一个 MonitorChannel。
I03：后端接受一条合法的人工观测值。
I04：后端拒绝跨项目或不存在通道的观测值。
I05：页面提交观测值并显示明确结果。
I06：页面显示业务时间上的最新观测值。
I07：页面显示该通道的历史观测值。
```

随后补充与当前风险对应的证据推进单元：

```text
E01：进程和数据库重启后观测值仍然存在。
E02：未认证和未授权请求无法读取或写入数据。
E03：重复提交不会产生未经定义的重复业务事实。
E04：能够从观测值找到来源、操作者和接收时间。
```

实际决策、名称、数量和顺序必须在该前沿真正开始时重新确认。

这个例子只说明：

* 全景可以长期稳定；
* 当前设计可以非常细；
* 远期步骤不需要提前伪造；
* 设计、实现和证据可以在一个小范围内完整闭环。

## 十二、每轮完成后的学习和用户掌握

Monitra 的推进既要形成生产能力，也要让用户真正理解系统。

每个当前前沿结束后，Codex 必须说明：

* 这次让业务主干向前移动了什么；
* 请求或事件从哪里进入；
* 哪个地方执行核心业务规则；
* 哪些状态发生了变化；
* 数据如何保存和查询；
* 权限、追溯和失败处理在哪里；
* 测试和运行证据在哪里；
* 哪些问题仍然没有设计。

用户练习与生产验收分开。

生产验收以功能、测试、运行和追溯证据为准。

用户练习用于帮助理解，可以包括：

* 找到入口和业务规则；
* 运行一个测试；
* 增加一个测试样例；
* 调整一个演示配置；
* 在练习分支完成一个不改变产品决定的小修改。

不得为了完成练习，随意改变没有业务依据的正式规则。

---

## 十三、禁止的推进方式

以下方式不再使用：

* 一次性写出从 V0.0 到 V1.0 的全部详细版本和微步骤；
* 把尚未设计的对象名称和状态模型写成未来 Ticket；
* 因为路线表中下一个编号存在，就自动进入开发；
* 先建立完整 CRUD，再寻找真实业务消费者；
* 按数据库表或技术分层拆 Ticket；
* 把权限、审计、备份、恢复和可观测性全部留到最后；
* 在真实需求出现前建设复杂平台抽象；
* 让 GIS、三维、大屏或 AI 自动成为核心主干的必经步骤；
* 用临时模型换取短期页面效果；
* 用当前代码反过来定义尚未决定的产品事实；
* 把绿色测试等同于完整业务验收；
* 让某个推进单元结束后留下无法说明上游来源或下游去向的孤立对象。

## 十四、这套计划如何保证最终形成完整系统

边设计边推进不等于没有方向，也不等于只做眼前功能。

完整性由四种机制保证：

```text
inspire.md
保证最终业务世界和产品方向不丢失；

系统全景与能力证据台账
保证随时看见已经完成、尚未闭环和仍待设计的能力；

滚动的当前前沿
保证只有最近的一小段被详细设计和实现；

每轮的运行与追溯证据
保证系统不是文档上前进，而是真的形成了可运行能力。
```

Monitra 的实际推进节奏因此是：

```text
看完整业务世界
→ 找到当前最值得解决的一处不确定性
→ 完成一个设计决策
→ 形成一个很小的正式 Spec
→ 拆成少量可验收行为
→ 实现并取得真实运行证据
→ 回写领域知识和能力全景
→ 重新选择下一前沿
```

系统始终有完整方向，但只有当前最近的一段拥有详细步骤。

这就是 Monitra 在权威设计尚未全部形成时，既避免盲目开发，又能够持续向完整系统推进的方式。
